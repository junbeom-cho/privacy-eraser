# ADR-013 : PK·UK 컬럼은 부분 마스킹 대신 결정적 해시로 바꾼다

* 작성일자 : 2026-08-14
* 작성자 : 조준범

## 1. 배경

개인정보가 PK 나 UNIQUE 에 걸려 있는 경우가 있습니다. 주민등록번호를 PK 로 쓰거나 이메일에
UNIQUE 가 걸린 식입니다. 실제로 `EMPLOYEES.EMAIL` 이 `EMP_EMAIL_UK` 에 걸려 있었습니다.

이런 컬럼은 지금 이관 자체가 막힙니다([ADR-005](ADR-005.md)). 마스킹하면 값이 겹쳐 제약조건을
만들 수 없기 때문입니다. 사용자가 할 수 있는 일은 **비대상으로 바꾸는 것뿐**인데,
그러면 PK 자체가 개인정보인 경우 비식별화에 실패합니다.

여기서 분명히 해야 할 것이 있습니다. **부분 마스킹으로는 이 문제를 풀 수 없습니다.**
부분 마스킹은 정보를 지우는 연산입니다. `010-1234-5678` 과 `010-9999-5678` 이 둘 다
`010-****-5678` 이 되는 것이 목적입니다. 고유성은 정반대로 **서로 다른 입력이 서로 다른 출력**이
될 것을 요구합니다. 한 연산이 둘을 동시에 만족할 수 없습니다.

그래서 질문이 "마스킹을 어떻게 고치나" 가 아니라 **"PK·UK 에는 어떤 다른 연산을 쓰나"** 가 됩니다.

## 2. 결정

PK·UK 컬럼에는 **결정적 해시**를 씁니다. 부분 마스킹과 나란히 고를 수 있는 또 하나의 종류입니다.

```sql
LOWER(RAWTOHEX(STANDARD_HASH(BMNO || '<솔트>', 'SHA256')))
```

`STANDARD_HASH` 는 **Oracle 12c 부터 내장된 SQL 함수**라 아무 권한도 필요 없습니다.
`DBMS_CRYPTO` 는 `EXECUTE` 권한이 따로 필요한데, 받은 DB 에서 그걸 기대할 수 없다는 것을
[ADR-003](ADR-003.md) 에서 이미 겪었습니다.

**Argon2 는 쓰지 않습니다.** 대입 비용을 올리려고 일부러 느리게 만든 함수라 한 건에 60ms 입니다.
489만 행에 키 컬럼 셋이면 250시간이 되고, 무엇보다 SQL 안에서 돌지 않아 데이터를 애플리케이션으로
꺼내야 합니다. [ADR-002](ADR-002.md) 가 무너집니다.

버린 대안은 셋입니다.

| 방식 | 왜 안 골랐나 |
|---|---|
| 대상에서 제외 (지금) | PK 자체가 개인정보면 비식별화에 실패합니다 |
| 마스킹하고 제약조건은 안 만듦 | 개발용 DB 에 없는 보장을 있다고 믿게 됩니다([ADR-005](ADR-005.md)와 같은 이유) |
| 순번 치환 | 형식은 살지만 **테이블 간 값이 어긋납니다**. 아래 참고 |

## 3. 결과

- **고유성이 유지됩니다.** 서로 다른 값은 서로 다른 해시가 되므로 PK·UNIQUE 를 만들 수 있습니다.
- **FK 가 따라옵니다.** 같은 입력에 같은 출력이라, 부모·자식에 같은 설정만 걸면 관계가 그대로입니다.
  값이 겹치지 않아야 부모의 PK 가 만들어지고, 그래야 FK 도 걸립니다.
- **`CREATE TABLE ... AS SELECT` 한 문장 안에 그대로 들어갑니다.** 데이터가 DB 밖으로 나가지 않습니다.
- 타입이 바뀝니다. 해시는 64자 hex 라 `NUMBER` PK 도 `VARCHAR2` 가 됩니다.
  마스킹 컬럼이 이미 그랬지만, **PK 타입이 바뀌면 그 위에서 개발하는 쪽 영향이 훨씬 큽니다.**
- [ADR-005](ADR-005.md) 의 사전 검사를 손봐야 합니다. 지금은 PK·UK 마스킹을 무조건 막는데,
  해시로 지정한 컬럼은 통과시켜야 합니다.
- 솔트를 어떻게 다룰지는 [ADR-014](ADR-014.md) 에서 정합니다.

### 참고 · 순번 치환을 쓰지 않는 이유

`12가3456` 을 `00가0001` 처럼 바꾸면 형식이 살아 개발하는 쪽이 편합니다. 매핑 테이블 없이
SQL 한 줄로도 됩니다.

```sql
'00가' || LPAD(DENSE_RANK() OVER (ORDER BY TWVHRNO), 4, '0')
```

문제는 **순번이 테이블마다 따로 매겨진다**는 점입니다. `DENSE_RANK` 는 값 하나가 아니라
그 테이블에 무엇이 들어 있느냐로 결정되기 때문입니다. 같은 차량번호가 테이블마다 다른 번호가 됩니다.

실제 스키마에서 `TWVHRNO` 는 **19개 테이블**에 퍼져 있고, PK·UNIQUE 에 쓰이는 컬럼 139개 중
**82개가 여러 테이블에 걸쳐** 있습니다. 과반이 순번을 쓸 수 없습니다.

더 나쁜 것은 **이 실패가 조용하다**는 점입니다. 이 스키마에는 **FK 가 하나도 선언되어 있지 않아
(PK 128 · CHECK 1062 · FK 0)**, 값이 어긋나도 이관은 성공합니다. 조인이 0건이 되는 것을
개발이 한참 진행된 뒤에야 알게 됩니다. FK 가 선언되어 있었다면 제약조건을 만들 때
`ORA-02298` 로 즉시 실패했을 것입니다.

해시는 **값 자체에서 결과가 나오므로** 테이블이 몇 개든, 관계가 선언되어 있든 아니든 항상 맞습니다.
FK 가 없는 스키마일수록 해시가 안전한 선택입니다.

형식이 꼭 필요한 컬럼이 실제로 나오면, 19개 테이블의 값을 모아 매핑 테이블을 만들고 조인하는
방법이 있습니다. 다만 어떤 컬럼끼리 같은 값 공간인지 알 방법이 없고(FK 가 없으므로 컬럼명으로
추측해야 합니다), 매핑 테이블 자체가 원본과 결과를 나란히 담은 표라 이관 후 반드시 지워야 합니다.
그때 가서 만듭니다.
