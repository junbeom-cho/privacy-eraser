# ADR-014 : 해시 솔트는 이관마다 새로 만들고 보관하지 않는다

* 작성일자 : 2026-08-14
* 작성자 : 조준범

## 1. 배경

[ADR-013](ADR-013.md) 의 해시에는 솔트가 필요합니다. 주민등록번호는 경우의 수가 10^13 정도라
솔트 없는 SHA256 은 전수 대입으로 뚫립니다.

솔트를 **보관할지**가 갈림길이었습니다. 보관하면 되돌릴 수 있는 가명정보, 버리면 익명정보입니다.

처음에는 보관 쪽으로 기울었습니다. 재이관할 때 같은 해시가 나와야 이관본 위에서 개발하던 사람의
참조가 안 깨진다고 봤기 때문입니다.

**그 근거가 약했습니다.** 이관은 원본 이름의 테이블을 전부 지우고 다시 만듭니다. 한 번 돌 때마다
모든 해시가 같은 솔트로 함께 갱신되므로 **이관본 내부 정합성은 항상 맞습니다.**
FK 도 그 안에서 맞춰집니다. 재이관 일관성은 문제가 되지 않습니다.

## 2. 결정

이관을 시작할 때 `SecureRandom` 으로 32바이트 솔트를 만들어 **그 실행 안에서만 쓰고 버립니다.**
어디에도 저장하지 않습니다.

**키 파생 함수를 쓰지 않습니다.** Argon2 같은 KDF 는 약한 비밀을 늘리는 도구입니다.
`CREDENTIAL_SECRET` 은 사람이 `.env` 에 타이핑하는 값이라 늘려야 하지만([ADR-001](ADR-001.md)),
솔트는 우리가 만드는 값이라 처음부터 2^256 으로 만들면 됩니다. 이미 강한 값을 늘릴 것이 없습니다.

## 3. 결과

- **아무도, 언제도 되돌릴 수 없습니다.** 익명정보입니다.
- DB 변경이 없습니다. 솔트 컬럼도, 암복호화도, 수명 관리도 필요 없습니다.
  보관하기로 했다면 `project.hash_salt` 컬럼과 Flyway 마이그레이션과 암복호화가 따라왔을 것입니다.
- 재이관하면 해시값이 전부 달라집니다. 이관본 내부는 문제없지만,
  **이관본 밖에 적어둔 값은 의미를 잃습니다** — 개발자가 이관 대상 스키마에 따로 만든 테이블의 참조,
  테스트 픽스처, 버그 리포트에 적힌 값 같은 것들입니다. 좁은 경우라 감수합니다.
- **검수 화면에서 마스킹 결과를 미리 보여줄 수 없습니다.** 솔트가 이관 시점에 정해지기 때문입니다.
  임시 솔트로 계산해 보여주면 실제 결과와 달라 더 헷갈립니다. 값 대신
  `해시로 대체됩니다` 라고 표시합니다. 해시값은 사람이 눈으로 확인할 것이 없습니다.
- 솔트는 SQL 문장에 문자열로 들어갑니다. Oracle 은 DDL 에 바인드 변수를 허용하지 않아
  `V$SQL` 에 남을 수 있습니다. 다만 그 SQL 을 실행하는 계정은 어차피 원본을 읽을 수 있어
  새로 열리는 것이 없고, 실행이 끝나면 솔트는 버려집니다.
