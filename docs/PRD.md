# Privacy Eraser

---
## 개발 목적
DB에서 개인정보 또는 특정 컬럼을 비식별화(마스킹) 해야할 때 GUI로 이를 해결하고자 개발합니다.

## 전체 흐름
원본 스키마(`raw_schema`)를 읽어 마스킹한 뒤, 결과를 별도 스키마(`edit_schema`)로 이관합니다.
**원본은 어떤 경우에도 수정하지 않습니다.**

```
프로젝트 생성 → 원본 스캔 → 키워드·정책 설정 → 판정 → 사람이 검수 → 이관 실행
   (원본 접속)   (테이블·컬럼)                  (제안)    (확정)    (edit 접속)
```

이관 대상 접속 정보는 프로젝트를 만들 때 받지 않습니다. 그 시점에는 어떤 테이블을 다룰지도
정해지지 않았고, 이관처 없이도 스캔·판정·검수가 전부 가능하기 때문입니다. 실행할 때 정합니다.

## 주요 기능
### DB 접속 및 읽기
- 타겟 DB에 접속하면 그 안에 테이블 및 컬럼 정보를 읽어옵니다.
- 타겟 DB는 우선 Oracle 만 진행하고 나머지는 추후에 추가합니다.
- 스키마와 테이블을 선택할 수 있습니다.
- 컬럼은 주로 표준화가 되어있고 Convention은 `_`로 구분하여 단어를 붙이는 형식(`T_usr_mstr`)이기 때문에 `_`를 기준으로 분리합니다.

### 키워드 및 정책 설정
- 키워드는 `Do`, `Undo` 로 나뉩니다.
- `Undo` 키워드가 포함되는 컬럼은 비식별화 대상에서 제외됩니다.
- `Do` 키워드가 포함되는 컬럼은 비식별화 대상이 됩니다.
- `Do`와 `Undo`가 함께 있을 시 비식별화 대상에서 제외됩니다. 우선권은 `Undo`에게 있습니다.
- 키워드와 정책은 함께 설정되며 정책의 내용은 위치(앞에서부터/뒤에서부터), 마스킹 개수로 이루어집니다.
- **키워드는 프로젝트마다 따로 관리합니다.** 프로젝트가 다르면 키워드도 정책도 공유하지 않습니다.
- **키워드 하나에 정책 하나입니다.** `phone`은 뒤 4자리, `name`은 앞 1자리처럼 키워드별로 다르게 둘 수 있습니다.
- `Undo` 키워드에는 정책이 없습니다. 제외하는 것이 전부이기 때문입니다.

### 비식별화 컬럼 설정
- 기본적으로 키워드 기반으로 비식별화 컬럼 여부를 결정합니다.
- 컬럼 표준화가 잘 된 데이터를 대상으로 하므로 문자열 패턴 분석 없이 키워드 기반으로 시작합니다.
- **키워드 판정은 최종 결정이 아니라 제안입니다.** 아래 검수 단계에서 사람이 확정합니다.

### 검수 (사람이 확인하고 고치는 단계)
키워드만으로는 놓치거나 잘못 잡는 컬럼이 반드시 생깁니다. 판정 결과를 표로 펼쳐 두고
사람이 눈으로 확인한 뒤 고칠 수 있어야 합니다.

- 프로젝트의 모든 테이블·컬럼을 한 화면에서 봅니다. 한 줄에 다음을 함께 보여줍니다.

  | 항목 | 설명 |
  |---|---|
  | 테이블 / 컬럼 | 대상 위치 |
  | 마스킹 여부 | 대상인지 아닌지 |
  | 판정 근거 | 어떤 키워드에 걸렸는지, 혹은 사용자가 직접 정했는지 |
  | 정책 | 방향(앞/뒤) + 마스킹 문자 수 |
  | 실제 데이터 | 원본에서 1개 행을 읽어 보여줍니다 |

- 사용자는 마스킹 여부와 정책을 **컬럼 단위로 덮어쓸 수 있습니다.** 덮어쓴 값이 키워드 판정보다 우선합니다.
- 실제 데이터를 보여주는 이유는 컬럼명만으로는 판단이 안 되기 때문입니다.
  다만 이 값은 진짜 개인정보이므로 **화면에만 표시하고 로그·캐시에 남기지 않습니다.**
- 원본에 컬럼이 추가되면 다시 스캔합니다. 재스캔 시 **사용자가 직접 고친 항목은 유지하고**
  새로 발견된 컬럼만 키워드로 판정해 추가합니다.

### 비식별화
- 비식별화 대상의 컬럼은 `*`을 통해 마스킹됩니다.
- `Undo` 키워드에 없고 `Do` 키워드에 존재하면 정책에 맞게 마스킹됩니다. 단 검수에서 덮어쓴 값이 있으면 그것이 우선합니다.

#### 값이 정책보다 짧을 때
마스킹할 문자 수가 실제 값의 길이보다 클 수 있습니다(정책은 4자리인데 값이 3자). 이때 동작은
**프로젝트 설정으로 사용자가 고릅니다.**

| 선택 | 동작 |
|---|---|
| 전체 마스킹 | 값 전체를 `*`로 바꿉니다 |
| 그대로 두기 | 마스킹하지 않고 원본 값을 유지합니다 |

어느 쪽을 고르든 **사용자가 그런 컬럼이 있다는 사실을 알 수 있어야 합니다.** 검수 화면에서
표본 값이 정책보다 짧은 컬럼을 표시하고, 이관 후에도 몇 건이 해당됐는지 알려줍니다.

- NULL 값은 마스킹하지 않고 NULL로 둡니다.

### 이관
이 도구의 결과물은 **다른 시스템을 개발할 때 쓰는 DB**입니다. 데이터만 옮기면 부족하고
제약조건·인덱스까지 원본과 같아야 그 위에서 정상적으로 개발할 수 있습니다.

- **원본 스키마의 모든 테이블을 이관합니다.** 마스킹 대상이 없는 테이블도 그대로 복사합니다.
- 이관 대상 스키마(Oracle 사용자)는 DBA가 미리 만들어 둔 것을 씁니다.
  도구는 그 안에 객체를 만들 뿐이며 `CREATE USER` 권한을 요구하지 않습니다.
- **원본과 이관 대상은 같은 Oracle 인스턴스입니다.** 그래서 데이터를 애플리케이션으로 꺼내지 않고
  DB 안에서 집합 연산으로 처리합니다. 마스킹은 SQL 식으로 표현됩니다.
- 원본 스키마와 이관 대상 스키마가 같으면 실행을 거부합니다. 원본을 덮어쓰게 되기 때문입니다.

#### 복제 범위

| 복제함 | 복제하지 않음 |
|---|---|
| 테이블 구조 (컬럼·타입·DEFAULT·NOT NULL) | 트리거 |
| PK / FK / UNIQUE / CHECK | 저장 옵션 (테이블스페이스·파티션) |
| 인덱스 | 권한(GRANT) |
| 컬럼·테이블 코멘트 | |
| 시퀀스 | |

트리거를 제외하는 이유는 마스킹된 데이터를 넣을 때 트리거가 돌면 값이 다시 바뀌거나
감사 로그가 오염되기 때문입니다.

#### 실행 순서
순서를 지키지 않으면 실패합니다.

1. 기존 객체 삭제 — **원본에 같은 이름이 있는 테이블로 한정합니다.** 이관 대상 스키마를 통째로
   비우지 않습니다. 접속 정보를 잘못 넣었을 때 피해를 줄이기 위해서입니다.
2. 테이블 생성 — 원본 DDL을 뽑아 스키마명만 바꿔 실행합니다. 이 단계에서는 제약조건을 뺍니다.
3. 데이터 적재 — 테이블별로 마스킹 식을 적용해 `INSERT ... SELECT` 합니다.
4. 인덱스 생성 — **적재 후에 만듭니다.** 적재 중에 인덱스가 있으면 행마다 갱신 비용이 듭니다.
5. PK / UNIQUE / CHECK 추가
6. **FK 추가 — 반드시 맨 마지막입니다.** 모든 테이블의 적재가 끝나기 전에 걸면
   참조 대상이 아직 없어 실패합니다.

#### 마스킹과 제약조건 (시작 전에 막습니다)
대부분의 테이블은 PK가 대리키(serial id)이고 FK도 그 id를 참조하므로 개인정보 컬럼에
제약조건이 걸리지 않습니다. 부딪히는 경우는 자연키에 UNIQUE가 걸린 때입니다(이메일·휴대폰 등).
마스킹된 값이 서로 겹쳐 제약조건을 만들지 못합니다.

**하나라도 실패하면 전체를 실패로 봅니다.** 일부만 제약조건이 걸린 스키마는 완전한 줄 알고
쓰이면 더 위험하기 때문입니다. 그래서 데이터를 옮기기 전에 막습니다.

- **검수 화면**에서 컬럼마다 `PK` / `UQ` / `FK` 를 표시합니다. 값이 겹치면 안 되는 컬럼을
  마스킹 대상으로 두면 경고하고 다음 단계로 넘어가지 못하게 합니다.
- **이관 시작 시점**에 다시 검사해, 충돌이 있으면 아무것도 옮기지 않고 어떤 컬럼의 어떤
  제약조건인지 알려줍니다.

사용자는 해당 컬럼을 비대상으로 바꾸고 다시 실행합니다.

#### 이관 후 통계
검수 화면의 경고는 **표본 1행** 기준입니다. 표본이 긴 값이면 경고가 뜨지 않고, 짧은 값이면
과하게 걱정하게 됩니다. 실제로 몇 건이 통째로 가려졌는지는 전수를 세야 알 수 있습니다.

이관이 끝나면 마스킹 컬럼마다 전체 행수와 **값 전체가 `*` 로만 남은 행수**를 세어 보여줍니다.
한 건도 없는 컬럼은 알릴 것이 없으므로 목록에서 뺍니다.

컬럼마다 따로 세면 테이블을 그 수만큼 훑게 되므로, 테이블 하나를 한 문장으로 한 번만 읽습니다.
집계에 실패해도 **이관은 성공입니다.** 데이터는 이미 다 옮겨졌고 이것은 보고서일 뿐입니다.

#### 실행 방식
- 수백만 행 기준으로 수십 초에서 몇 분이 걸립니다. HTTP 요청 하나로 처리하면 중간에 끊깁니다.
- **비동기로 실행합니다.** 요청하면 실행 ID를 돌려주고, 화면은 상태를 따로 조회합니다.
- 진행 상황(전체 테이블 수 / 완료 수 / 현재 테이블)과 실패 사유를 남깁니다.
- **재실행하면 지우고 새로 만듭니다.** 이관 결과는 원본에서 다시 만들 수 있는 파생물이라
  누적할 이유가 없고, 정책이 바뀌면 이전 결과는 어차피 틀린 값이 됩니다.
